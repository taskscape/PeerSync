# P2 native SCM and initialization verification

On 2026-10-22, a temporary local `PeerSync` service was created from the Release apphost under the virtual account `NT SERVICE\PeerSync`, with its service SID enabled. The native `--init` path created the protected `%ProgramData%\PeerSync` config/state/log folders, settings, an ECDSA P-256 machine key and self-signed device certificate, a free TCP/UDP port, and the Application Event Log source. Repeating `--init` preserved the existing settings and returned success.

The first run exposed two initialization defects. The service SID was looked up as `COMPUTERNAME\NT SERVICE\PeerSync` instead of the virtual-account authority `NT SERVICE\PeerSync`. Also, CNG rejected setting the security descriptor without `DACL_SECURITY_INFORMATION`; after correcting the selector, the descriptor needed to be applied to the persisted key. The service startup then exposed a third defect: certificate lookup required a trusted chain, even though device certificates are self-signed and authenticated by the configured thumbprint. The loader now selects by thumbprint and enforces the device key and validity checks without requiring chain trust. A regression test verifies that behavior.

SCM started the service as `NT SERVICE\PeerSync`. The service loaded its configured machine certificate, opened state and reported `service.control_ready`. The default verified CLI read status over the named pipe. Adding an isolated temporary folder through `psp add` caused the installed runtime to bind its configured QUIC UDP port and start LAN discovery. No Windows Firewall prompt appeared during this local bind. SCM stop completed in about seven seconds and logged `service.stopped`; the host's configured shutdown timeout is 15 seconds.

The documented `--remove-data` command then removed the generated machine certificate and CNG key and deleted only `%ProgramData%\PeerSync`. The temporary SCM registration, service-only local group, event source and isolated share were removed afterward. Final checks found no PeerSync service, data root, event source, test group, test share or `CN=PeerSync Device` certificate. The pre-existing `PeerSync Development` and CI signing certificates remained in the machine store.

This verifies local Windows initialization, virtual-account key access, SCM start/stop, named-pipe client control, QUIC listener startup and data removal. It does not provide an authenticated remote peer session through SCM, TCP service fallback, real clock-skew recovery through SCM, rendered WPF status, physical LAN/NAT evidence, or the 72-hour soak. Those P2/P4 requirements remain open. The canonical full local verifier must be rerun after these fixes; the earlier same-day pass predates them.
