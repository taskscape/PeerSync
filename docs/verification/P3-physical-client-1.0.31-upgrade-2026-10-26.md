# Three physical clients: development 1.0.31.0 upgrade

The first, second and third LAN PCs were upgraded from 1.0.28.0 to a development-signed 1.0.31.0 build from committed source `6982d3ab7b43594447b897eac76f6e5548f59192`. This carries the Windows 11 service cold-start repair, LAN membership refresh, CLI service-folder ACL grant and WPF protected-child warning. It is a field upgrade check, not a release build or an app-only onboarding check. Later commits changed the installer runtime prerequisite and the corpus generator; this field package does not cover those subsequent packaging changes.

The normal `Build-Installer.ps1` attempt stopped before publish because locked restore could not open `WinRT.SourceGenerator.dll`. The committed build script's development-only `-UseExistingRestoredAssets` path then built all three self-contained ReadyToRun components and signed the x64 installer. The manifest explicitly says `restoreMode: existing-assets`, `localDevelopmentOnly: true`, `publicReleaseSigning: false`, version 1.0.31.0 and the source revision above. `workingTreeDirty: true` is caused by the preserved unrelated untracked `Sync.zip.tmp`; no tracked source input was changed after the commit. The local-only fallback does **not** prove locked-restore parity. Its release-build negative control rejects `-UseExistingRestoredAssets` without a development switch.

The setup SHA-256 is `7BE0014A26E1E743F97A33BC30AE31225C2022B0BA23F8D5CA476BF5B0A69122`. Authenticode reports Valid with development signer `6AE1CBFC31F1DB189AF03A82D60C535AE8E0A7BD`; the adjacent manifest hash matches.
