# P1.2 chunking and file hashing — 2026-10-19

P0's SHA-256-derived gear table and all three normalized FastCDC size classes
remain unchanged. A stdlib-only Python absolute-position reference independently
generates golden chunk lengths for a 16 MiB + 17 byte SHA-256 counter corpus.
Tests reconstruct the corpus, verify its SHA-256 and compare every boundary
at read sizes 4,093, 65,536 and 1,000,000 for all three classes. Existing tests
also cover one-/seven-byte reads, empty inputs and exact windows. Regenerate
with `build/Generate-FastCdcVectors.py`; normal .NET tests require no Python.

A fresh pass over the existing 10 GiB reference corpus initially missed the
1 decimal GB/s target. Hoisting masks and iterating sliced spans with a fixed
256-entry gear span makes bounds visible to the JIT and reduces hot-loop
overhead without changing cut rules.
Both passes produced 3,840 chunks and identical whole-file BLAKE3:

| Native implementation | Seconds | Decimal GB/s |
| --- | --- | --- |
| Original loop, fresh measurement | 11.6744 | 0.9197 |
| Fixed gear span / slice iteration | 9.9605 | **1.0780** |

The managed comparison improved from 0.8539 to 0.9577 GB/s. Production uses
Blake3.Native 3.0.2 as selected in P0. Timings exclude corpus generation and
use the same repeated-random-block, warm-cache corpus described in
[P0.2.4](../spikes/P0.2.4-chunking-hashing.md) on the
[reference PC](../reference-hardware.md). This does not claim cold-disk or
Arm64 throughput. Raw local evidence: `artifacts/p1-chunk-benchmark*.log` and
`artifacts/p1-hash-environment.json`.

The file hasher streams once through the shared chunk reader, native BLAKE3
whole/chunk hashing, and a length-bounded stream. Native handle metadata tracks
size, last-write/change time, attributes and 128-bit file identity plus volume.
After reading, both the original handle and reopened path must match. Detected
mutation/removal/replacement returns null for retry. I/O/access failures and
cancellation propagate. Shared writers/deletion are allowed; reparse files
are rejected. Progress exposes only byte/chunk counts. Metadata checks are
not an atomic snapshot and cannot prevent a writer changing the file after
the final check; watcher/rescan recovery remains required.

Local focused validation: 11 Crypto cases and 13 Engine cases pass, zero
skipped. Engine tests cover empty/ordinary files, independent hash comparison,
chunk offsets, progress, shared/exclusive locks, mid-read overwrite with
restored mtime, truncation, growth, replacement, rename, deletion, cancellation
and symlink rejection. Scoped Engine/Crypto analyzers are clean with no load
warnings or truncation. The canonical runner includes Engine tests. Full
runner/CI verification remains in progress; both tasks stay WIP until merged
with green CI.
