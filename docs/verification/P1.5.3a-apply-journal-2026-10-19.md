# P1.5.3a durable apply journal — 2026-10-19

Migration 4 adds bounded opaque apply recovery state, a unique operation ID and
one pending operation per case-folded path, with its expected local sequence.
The engine will validate/version the payload and its root/file identities; the
storage layer does not interpret it as a protocol message. Intent objects own
their bytes, redact paths/payloads from JSON and `ToString`, and reject implicit
JSON deserialization. The maximum payload is 24 MiB, allowing a bounded signed
record plus recovery metadata without embedding file contents.

`Db.WriteDurableAsync` shares the existing single-writer queue. It switches to
FULL before starting a transaction and restores NORMAL after commit/rollback,
before completing the request. Ordinary scan batches retain NORMAL. SQLite's
[documented WAL synchronization semantics](https://www.sqlite.org/pragma.html#pragma_synchronous)
make FULL the required intent-before-filesystem commit boundary; tests inspect
that configuration, not physical power-cut behavior or disk-controller honesty.

Reservation checks the expected local sequence, is idempotent for the exact
same intent, and rejects another operation for the path. Recovery payload
rewrites compare exact previous state. Abandonment is explicit and allowed
only after the caller verifies no mutation or a safe filesystem rollback.
Pending intents survive reopening and must be processed before folder scans.

Completion compares intent/state and local sequence inside the writer's current
transaction. It writes the new local row, chunks and allocated sequence, new
archive rows, recomputes needed state from current local/all-remote records,
and removes the intent atomically. A later remote winner can remain needed.
Failed/cancelled callbacks roll back every table and keep the recovery intent;
exact completion retries do not allocate another sequence/archive row.
Queued completion owns mutable caller arrays/vectors/chunks before waiting.
Archive metadata must refer to this original path and distinct valid private
destinations; it cannot overwrite another archive ID.

All 36 Storage cases pass, including eleven added cases for durable mode and
queue draining, intent ownership/redaction/bounds, per-path reservation/replay,
compare-and-swap rewrites, reopen, atomic completion, rollback/cancellation,
local-state races, queued caller mutation and invalid archive metadata. The
v1 migration regression now verifies backups before v2/v3/v4 and schema 4.
Scoped Storage/Storage.Tests compiler/analyzer checks are clean, without load
warnings or truncation.

The canonical local runner passed 273 cases, native probes, diagnostics,
watcher recovery and probe publishing in 109.51 seconds, exit 0, with fuzz
explicitly skipped. The final archive-path check and two additional regressions
then passed all 36 Storage cases. A fresh one-million-row synthetic metadata
benchmark after the shared batch-writer refactor inserted/verified every row
with the correct high-water sequence in 5.75 seconds (target under 60 s),
326,524,928 database bytes. This is warm local SSD indexing with 1,000-row
NORMAL transactions, not file hashing/signing or FULL-sync apply throughput.

Evidence: `artifacts/p1-apply-journal-tests.log`,
`artifacts/p1-apply-journal-verification.log`,
`artifacts/p1-apply-index-benchmark.log` and matching TRX files.

P1.5.3a remains unchecked until green CI and merge. The filesystem coordinator,
engine recovery-payload codec, startup recovery, folder operation gate, archive
pruning and complete conflict-table integration still need implementation.
Storage primitives alone do not prove a crash-safe filesystem transaction.
