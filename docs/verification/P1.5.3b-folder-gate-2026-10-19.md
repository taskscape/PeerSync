# P1.5.3b folder operation gate and atomic capability check — 2026-10-19

Scans acquire the same per-index asynchronous gate that filesystem application
and recovery will use. A weak-key registry follows the index owner's lifetime;
no native wait handle is exposed or allocated. Cancellation releases the
scanner's private gate, and disposing a lease twice cannot release it twice.
Different folder index owners remain independent. The service still owns one
index per configured root and must stop operations before disposing it.

Before walking, Scanner checks for pending apply intent and fails closed.
It cannot publish an interrupted application's missing target as a signed
local deletion. Recovery must resolve or safely park pending work first.
Four integration cases cover blocking/release, cancellation and subsequent
rescan, a retained original/missing-target interval with no deletion published,
safe rollback before resuming, and independent folder owners.

Native mutation support adds no-overwrite hard-link retention and a guarded
FileRenameInformationEx capability check. The latter verifies target identity
and holds its guard. On this local Windows machine, replacement/POSIX/
ignore-readonly flags still return sharing violation 32 with the no-delete-
sharing guard held, for both normal and read-only originals. Target, temporary
data and archive link remain intact. A wrong guard and occupied archive name
also fail without clobbering data.

The native test records capability in TRX rather than assuming all Windows
versions behave identically. A supported result must preserve the original
archive/guard and install the exact replacement identity; an unsupported
sharing violation must leave both names/data unchanged. Local TRX reports
`guardedAtomicReplacementSupported=False` in both cases. This test performs
neither File.Replace nor replacement through a symbolic link.

All 103 Engine cases pass. The canonical local runner passed 282 cases,
native probes, diagnostics, watcher recovery and publishing in 107.25 seconds,
exit 0, with fuzz explicitly skipped. The final portable capability-reporting
adjustment then passed all 103 Engine cases separately. Evidence:
`artifacts/p1-apply-gate-tests.log`, `artifacts/p1-apply-gate-verification.log`,
`artifacts/tests/p1-apply-gate/` and the native capability log.

P1.5.3b is incomplete. No working installation primitive or startup recovery
coordinator is claimed. The [atomicity proposal](../proposals/P1-atomic-replacement-recovery.md)
is awaiting the user's decision. Strict atomicity remains required unless the
specific recoverable two-move protocol is explicitly approved. Other P1
requirements, no-lost-version checks and every gate remain unchanged.
