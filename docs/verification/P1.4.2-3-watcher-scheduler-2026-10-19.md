# P1.4.2/P1.4.3 watcher and scheduler — 2026-10-19

The native watcher uses a 64 KiB buffer and bounded notification/pending-path
state (8,192 entries each). Its callbacks only enqueue or set overflow flags.
The consumer coalesces paths case-insensitively, includes both rename paths,
prunes internal metadata/temp paths and uses monotonic time: 2 seconds quiet,
or a maximum 30 seconds from the earliest notification. Native errors, queue
saturation and pending-set saturation emit a full-scan request. Drains are
bounded so a hot producer cannot starve the debounce tick. Cancellation releases
the single-consumer guard; disposal wakes an idle consumer and releases native
watcher resources. No arbitrary callback runs in the native event handler.

The scheduler subscribes before startup scanning and coalesces startup,
periodic (default 600 seconds) and debounced watcher requests. Ready batches
currently schedule a complete safe walk; unchanged metadata avoids hashing.
Restarting a native watcher schedules a scan to cover the subscription gap.
Transient read/enumeration problems retry at 10, 20, 40, 80, 160, 320 and then
600 seconds. Retry waits release the scan budget and cancellation drains all
producers/consumers. The caller owns scanner/index/key lifetimes and must cancel
and await the scheduler before disposing them.

The initial process-wide single-folder permit enforces the per-disk limit even
for multiple partitions, shared disks and unknown physical mappings. Independent
disk parallelism is a future performance refinement; there is no current claim
of parallel scans on separate disks. Per-file hashing remains bounded within a
scan. Scanner content handles receive the Windows `IoPriorityHintVeryLow` hint;
native Windows accepted it in these tests. Driver scheduling behavior is a
hint, not a guaranteed bandwidth reservation. A rejected hint defers the read.

Watcher/scheduler diagnostics contain opaque session IDs, counts, reason codes,
retry delays and HResults/native errors without paths, contents or keys.
Scheduled-scan and scanner events also share a W3C trace ID. Status consumers
may read a bounded outcome stream; this is status telemetry, not a durable work
queue. Actual own-write integration is the puller's responsibility: the test
models its required metadata commit, then proves the queued event causes zero
hashes/versions. A production puller is not present yet.
