# P0.2.2 — Dial from the listener port

Question: can a listening peer dial from the same local port, so NAT mappings
can be reused? Tests ran 2026-10-18 on Windows build 26300, .NET 10.0.13,
MsQuic 2.5.11.159415436, x64.

| Option | What was actually tested | Local result |
| --- | --- | --- |
| (a) System.Net.Quic | Two listeners; outgoing `LocalEndPoint` set first to loopback plus listener port, then to the listener's wildcard endpoint | SocketException, WSAEADDRINUSE (10048) |
| (b) Direct MsQuic | Native API v2; two listeners; `QUIC_PARAM_CONN_SHARE_UDP_BINDING = TRUE`, same listener port, both wildcard and IPv4 listener families, client certificate supplied | Transport status 0x80072740 / WSAEADDRINUSE; no connection |
| (c) TCP simultaneous open | Two listeners and two outbound sockets; SO_REUSEADDR on every socket; outgoing sockets bound to the listening endpoints | SocketException; no verified simultaneous-open channel |

The managed and TCP modes are in `spikes/QuicPunch`. Native source is in its
`native/` directory. `build/Build-NativeBindingSpike.ps1` downloads MIT-licensed
headers from Microsoft/msquic commit `42376ae4b414ff80d8317aadb3e9e789400e7638`
and compiles with Visual C++ `/W4 /WX`. The driver uses the installed .NET
runtime's msquic.dll. Its certificate-validation bypass is confined to this
binding-feasibility spike; it is not a production authentication scheme.

Reproduce:

```powershell
dotnet run --project spikes/QuicPunch -c Release
./build/Build-NativeBindingSpike.ps1
dotnet run --project spikes/QuicPunch -c Release -- --native artifacts/msquic/shared-binding.exe
dotnet run --project spikes/QuicPunch -c Release -- --tcp
```

Managed/TCP exit 3 means the tested binding was unsupported, not a pass.
Native exit 1 means no verified shared binding. Ordinary loopback QUIC still
passes, so these failures are distinct from lack of QUIC support.

Microsoft's current binding lookup rejects a sharing request when the
server-owned flag differs. That source is consistent with the observation,
but was not instrumented inside the installed binary; it is supporting
evidence, not proof of that exact internal branch.

| Required topology | Result |
| --- | --- |
| Same physical LAN | Not run: second PC unavailable |
| Full-cone home NAT | Not run |
| Port-restricted home NAT | Not run |
| Mobile hotspot / CGNAT | Not run |

Provisional decision: direct QUIC/TCP on reachable endpoints, followed by
relay after five seconds for hard NATs. Coordinated punching is not claimed.
The design doc, plan decision log and P4.2.3 describe this provisional outcome.
2026-10-19 phasing update: the user explicitly deferred this physical NAT
matrix and final transport decision to Gate P4. The task remains unchecked;
implement direct QUIC/TCP followed by relay after five seconds as the approved
baseline while those checks are pending. No native-punch success is inferred
from loopback or the user's successful Tailscale transfer.
