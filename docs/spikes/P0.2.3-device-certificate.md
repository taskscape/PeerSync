# P0.2.3 — Machine certificate under a virtual account

Question: can Schannel use a persisted, non-exportable machine CNG P-256 key
under `NT SERVICE\PeerSyncSpike`, while a standard user cannot use the key?

`build/Run-ServiceP0.ps1` publishes to an isolated temporary ProgramData
directory, refuses existing spike services, creates the virtual service and
machine certificate, then runs both QUIC and SslStream mutual-TLS probes.
The private-key DACL explicitly allows SYSTEM, Administrators and this
service SID. The service gets GenericRead only. Provider default grants are
removed. An unrelated temporary standard user tries to sign using the key;
success is a test failure, and CryptographicException is the expected denial.

2026-10-18 result: QUIC and TCP/TLS 1.3 succeeded under the virtual account,
both certificate-derived identities matched, and the standard user's actual
private-key signing operation was denied. Evidence:
`artifacts/p0-services/virtual-account-tls.log`,
`standard-user-private-key-denied.stdout.log`, `summary.json`.

The finally block stopped/deleted both temporary services, removed the test
certificate and persisted key, removed the temporary account, and deleted its
isolated output tree. A follow-up inventory found no spike services, account,
machine-store spike certificate or ProgramData spike directory remaining.
Production services and synced folders were not involved.

Decision: retain the plan's persisted machine CNG key and service SID ACL.
Use a non-exportable signing key; never fall back to exporting a PFX for the
service. Repeat on Server 2022 and 2025 as the environment matrix becomes available.
