# P0.2.4 — FastCDC plus BLAKE3 throughput

Question: can a single sequential pass perform content-defined chunking,
per-chunk hashes and a whole-file hash at 1 decimal GB/s on the reference NVMe?
Do boundaries stay identical across different read sizes?

Reference hardware is in `docs/reference-hardware.md`. The harness uses a
10 GiB file made of repeated random 4 MiB blocks. This is a warm-cache test;
it does not claim cold-NVMe throughput or an incompressible full-size corpus.
Each implementation hashes the same file, with the same 3,840 cuts and the
same whole-file result. Timings exclude generating the corpus.

| Implementation / buffer approach | Seconds | Decimal GB/s |
| --- | --- | --- |
| Managed 3.0.2, initial per-chunk compaction | 15.938 | 0.674 |
| Native 3.0.2, initial per-chunk compaction | 13.561 | 0.792 |
| Managed 3.0.2, retained window / full buffer reads | 12.107 | 0.887 |
| Native 3.0.2, retained window / full buffer reads | 10.219 | **1.051** |

Decision: retain the 1 GB/s reference target and select `Blake3.Native` 3.0.2.
The `Blake3` package became managed in v3; `Blake3.Native` retains the original
native implementation. Both x64 and Arm64 runtime payloads exist in the
package. Arm64 execution/performance has not been tested.

`ChunkReader` waits for at least Max bytes or EOF before choosing a cut, uses
a pooled two-Max window, and compacts only when it needs more data. Tests
compare cuts at read sizes 1, 7, 4093, 65536 and 1000000, cover empty/exact
windows and chunk classes, and check BLAKE3 against the published empty/abc
vectors. Tests passed before and after the copy optimization. CI also runs
ten minutes of boundary fuzz smoke with reproducible integer seeds.

```powershell
dotnet run --project tests/PeerSync.Benchmarks -c Release -- <new-file> --create 10737418240
dotnet run --project tests/PeerSync.Benchmarks -c Release -- <existing-file>
dotnet run --project tests/PeerSync.Benchmarks -c Release -- --micro
```

The first command refuses to overwrite an existing file. It writes a large
test file; delete only the corpus you deliberately created after measurement.
`--micro` is the BenchmarkDotNet cut-point benchmark. The recorded numbers
above come from the end-to-end timed file harness, not BenchmarkDotNet.

Source: [Blake3.NET package split and API](https://github.com/xoofx/Blake3.NET).
