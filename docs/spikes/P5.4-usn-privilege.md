# P5.4 USN journal feasibility — partial spike, 2026-10-22

The question is whether the installed `NT SERVICE\PeerSync` virtual account
can query and read an NTFS volume change journal without broadening its
privileges. A successful query by an administrator does not answer that
question. No USN startup shortcut is enabled yet.

On the development PC, elevated PowerShell reported
`SeManageVolumePrivilege` and `SeBackupPrivilege` present but disabled, and
`fsutil usn queryjournal C:` returned the current journal identifier, first
USN and next USN. This shows only that the current elevated token can query
this NTFS volume. The installed service account has not been exercised.

Microsoft documents that `FSCTL_READ_USN_JOURNAL` uses a volume handle and
returns records between USN positions; `FSCTL_QUERY_USN_JOURNAL` supplies
the journal identifier. A saved cursor is only safe when it belongs to the
same journal identifier and is still at or above the journal's first valid
USN. References:
[read operation](https://learn.microsoft.com/en-us/windows/desktop/api/winioctl/ni-winioctl-fsctl_read_usn_journal),
[journal identifier](https://learn.microsoft.com/en-us/windows/win32/fileio/using-the-change-journal-identifier),
[record walk](https://learn.microsoft.com/en-us/windows/win32/fileio/walking-a-buffer-of-change-journal-records).

Next, run a minimal query-and-read probe as the actual service identity on
Windows 11, Server 2022 and Server 2025 with the installed data-path ACLs.
Record the volume filesystem, handle access mask, journal ID, first/next USN,
native error and effective privileges, without recording file names. If read
requires a new privilege or broad volume ACL, decide explicitly whether to
grant only the service SID that access or retain the existing full walk with
size/mtime short-circuiting. Do not silently run the service as administrator.

Even with access, a production shortcut needs a durable per-volume journal
ID/cursor committed only after scanning and index publication, a complete
file-reference-to-path mapping, rename/ancestor handling, and a forced full
walk on journal reset, cursor expiry, overflow, unsupported filesystem or
uncertain record parsing. `Scanner.ScanAsync` currently walks the tree and
performs apply-intent recovery before comparing entries; no USN result may
bypass either the recovery or native path/identity guards. These correctness
checks are prerequisites to enabling P5.4, rather than evidence that it is
done.
