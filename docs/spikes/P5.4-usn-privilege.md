# P5.4 USN journal feasibility — completed privilege spike, 2026-10-23

The question was whether the installed NT SERVICE\PeerSync virtual account
could query and read an NTFS volume change journal without broadening its
privileges. No USN startup shortcut is enabled.

On the development PC, elevated PowerShell reported
`SeManageVolumePrivilege` and `SeBackupPrivilege` present but disabled, and
`fsutil usn queryjournal C:` returned the current journal identifier, first
USN and next USN. This established the administrative control; the installed
service-account result is below.

Microsoft documents that `FSCTL_READ_USN_JOURNAL` uses a volume handle and
returns records between USN positions; `FSCTL_QUERY_USN_JOURNAL` supplies
the journal identifier. A saved cursor is only safe when it belongs to the
same journal identifier and is still at or above the journal's first valid
USN. References:
[read operation](https://learn.microsoft.com/en-us/windows/desktop/api/winioctl/ni-winioctl-fsctl_read_usn_journal),
[journal identifier](https://learn.microsoft.com/en-us/windows/win32/fileio/using-the-change-journal-identifier),
[record walk](https://learn.microsoft.com/en-us/windows/win32/fileio/walking-a-buffer-of-change-journal-records).

On a disposable Windows Server 2025 VM with the installed 1.0.9 service,
both a temporary scheduled task and a temporary Service Control Manager
binary ran as NT SERVICE\PeerSync and wrote only access results, not file
names. The SCM binary is [UsnServiceProbe](../../spikes/UsnServiceProbe);
the supplementary task script is
[UsnPrivilegeProbe.ps1](../../spikes/UsnPrivilegeProbe.ps1). Both agreed:

| Volume handle access | Account | Open | Journal query/read |
| --- | --- | --- | --- |
| Generic read | VM Administrator | succeeded | succeeded/succeeded |
| Generic read | NT SERVICE\PeerSync | error 5, access denied | not reached |
| File data read | NT SERVICE\PeerSync | error 5, access denied | not reached |
| Zero access | NT SERVICE\PeerSync | succeeded | query failed |

The temporary task was unregistered, and the SCM service command was
restored to the original PeerSync binary; the normal service returned to
Running. A VM snapshot named pre-p5-usn-probe-20261023 preserves the
pre-probe installed state. The SCM result reported Win32 error 5 for both
read handle types and error 1 for a zero-access journal query. The failure
is at the volume access boundary, before cursor or record parsing. Windows
11 and Server 2022 were not probed.

Decision: drop the optional USN optimization rather than grant the service
account a new volume privilege or broad volume ACL. Keep the existing full
walk with size/mtime short-circuiting and native path/identity guards. This
is the fallback explicitly permitted by plan.md P5.4. The separate P5.3
one-million-file performance target remains open and must be measured against
that fallback.

If this optimization is revisited, a production shortcut needs a durable
per-volume journal ID/cursor committed only after scanning and index
publication, a complete
file-reference-to-path mapping, rename/ancestor handling, and a forced full
walk on journal reset, cursor expiry, overflow, unsupported filesystem or
uncertain record parsing. `Scanner.ScanAsync` currently walks the tree and
performs apply-intent recovery before comparing entries; no USN result may
bypass either the recovery or native path/identity guards. These correctness
checks are prerequisites to enabling P5.4, rather than evidence that it is
done.
