# P0.2.5 — Named pipe across accounts

Question: can a virtual-account service serve gRPC to an authorized standard
user, deny an unauthorized user, preserve its pipe owner, and identify the
caller using `RunAsClient` with Identification-level impersonation?

The ControlPipe probe uses Kestrel HTTP/2, CurrentUserOnly=false and a
protected PipeSecurity ACL. Only the server SID receives CreateNewInstance;
Administrators and the explicitly authorized account receive ReadWrite.
The client checks the owner SID before sending any HTTP/gRPC bytes. It uses
TokenImpersonationLevel.Identification. The server's RPC calls RunAsClient
and returns the actual caller SID, not any client-supplied identity.

2026-10-18 results:

- Same-user gRPC passed; an intentionally wrong expected owner was rejected.
- `NT SERVICE\PeerSyncControlSpike` denied the unrelated standard user.
- After restarting with that standard user's SID explicitly authorized, the
  user connected, the owner check passed, and the returned SID matched the
  standard user's own token SID.

Evidence is in `artifacts/p0/pipe-*.log` and
`artifacts/p0-services/{authorized-standard-user,unauthorized-standard-user}.*.log`.
Temporary services/account/output were cleaned up by the service spike.
Decision: retain the explicit ACL, client owner check and per-call identity.
The production local group, per-call authorization and audit policy arrive
with P2/P3; this spike establishes the cross-account mechanism, not those RPCs.
